# TASK-010 — Production readiness

Статус: planned. Зависимости: 009.

## Цель

Довести реализованный MVP до проверенной готовности к первому релизу.

## Источники требований

AGENTS.md; docs/ROADMAP.md; docs/REQUIREMENTS.md; docs/TESTING.md. Дополнительно (пути относительно docs/): SECURITY.md, TESTING.md, REQUIREMENTS.md, ARCHITECTURE.md, ANALYTICS.md.

## Подзадачи и критерии приёмки

### TASK-010.01 — Аудит доступа

- [ ] Статус: planned.
- Зависимости: зависимости этапа, указанные выше.
- Реализация: Проверить весь API, cookies/CSRF, IDOR, RBAC, rate limit, CSP; написать regression tests и исправить выявленные дефекты. Проверить составные отношения, privacy jobs и P0 audit.
- Критерии приёмки: Матрица доступа двух владельцев проходит; нет известных критических/блокирующих проблем. Сквозной экспорт покрывает все P0 домены. Удаление при активном запуске закрывает новые операции и прекращает доступ.

### TASK-010.02 — Аудит sandbox

- [ ] Статус: planned.
- Зависимости: TASK-010.01.
- Реализация: Проверить runtime isolation, egress, CPU/RAM/PIDs/disk/time, процессную очистку и malformed fixtures; устранить недостатки.
- Критерии приёмки: На целевом Linux с AppArmor/cgroup v2 зафиксировать реальные digest и полный `TestLinuxRuntime` без skip. Подтвердить непривилегированный запуск, seccomp/AppArmor, закрытую сеть и отсутствие секретов, чужих файлов и Docker socket, read-only root, CPU/RAM/PIDs/диск и stop при отмене/timeout с потомками. Проверить restart reconciliation реального runtime и удаление workspace. Сквозной upload через реальный launcher публикуется только после успешной инспекции; при отключённом или несовместимом runtime публикация невозможна. Результаты обеих профильных сборок входят в обязательные доказательства для TASK-010.09.

### TASK-010.03 — Supply chain

- [ ] Статус: planned.
- Зависимости: TASK-010.02.
- Реализация: Добавить/запустить dependency, image и secrets scanning, SBOM при возможности; устранить критические находки и задокументировать исключения. Проверить lockfiles, лицензии, digest и supply chain, привязанные к реальным образам.
- Критерии приёмки: Отчёт с версиями и результатами сканирования; нет открытых критических дефектов. Точный состав образов и известные уязвимости задокументированы.

### TASK-010.04 — Нагрузочные тесты

- [ ] Статус: planned.
- Зависимости: TASK-010.03.
- Реализация: Написать scripts нагрузки API/upload/queue, normal и saturation cases; измерить p95, CPU/RAM/disk, fairness, backpressure. Использовать профили и методы REQUIREMENTS/TESTING.
- Критерии приёмки: Отчёт с окружением и фактическими результатами против утверждённых SLO; неуспешные цели исправлены либо пересогласованы. Проверены p95, LCP, saturation, ресурсы, fairness и граничные значения.

### TASK-010.05 — Backup/restore

- [ ] Статус: planned.
- Зависимости: TASK-010.04.
- Реализация: Написать автоматизированные scripts резервного копирования PostgreSQL и необходимых S3 объектов, шифрование, off-host retention; провести restore в отдельной среде. Выполнить ADR-002 с манифестом объектов и replay удалений до открытия трафика.
- Критерии приёмки: Восстановленная система читает согласованные записи/объекты; измерены RPO/RTO; секреты не включены в репозиторий. Подтверждены RPO/RTO, доступные результаты и отсутствие восстановленных удалённых данных.

### TASK-010.06 — Мониторинг

- [ ] Статус: planned.
- Зависимости: TASK-010.05.
- Реализация: Подготовить Prometheus/Grafana configs, приватные metrics, alerts на недоступность, queue lag, ошибки, storage, backup; проверить тестовую тревогу.
- Критерии приёмки: Тестовые сбои видны оператору; dashboards не содержат приватного содержимого.

### TASK-010.07 — Staging и HTTPS

- [ ] Статус: planned.
- Зависимости: TASK-010.06.
- Реализация: Написать production/staging Compose и Caddy конфигурации, healthchecks, persistent volumes, secrets injection, миграции и smoke scripts. Выбрать допустимые регион, S3, инфраструктуру и транзакционную почту до проверок с реальной инфраструктурой. Бюджет ориентировочный, расходы и внешние аккаунты требуют разрешения.
- Критерии приёмки: Локальная или разрешённая staging среда запускается с TLS; проверены health, migration и основные пользовательские потоки. На разрешённом стенде проверены доставка verify/reset, bounce/rate limit, S3 и HTTPS, независимая проверка auth/sandbox/deploy.

### TASK-010.08 — Релиз и откат

- [ ] Статус: planned.
- Зависимости: TASK-010.07.
- Реализация: Написать CI release workflow без автоматического production deploy, versioned images, процедуру отката и runbook incident/restore; выполнить rehearsal.
- Критерии приёмки: Проверен откат в тестовом окружении; инструкции воспроизводимы; реальные credentials не использованы.

### TASK-010.09 — Финальный gate

- [ ] Статус: planned.
- Зависимости: TASK-010.08, TASK-010.02.
- Реализация: Сверить P0, privacy/terms и применимые правовые требования, E2E, независимый человеческий review auth/sandbox/deploy; составить release checklist. Подтвердить выполнение всех обязательных P0 и зафиксировать оставшиеся production-условия.
- Критерии приёмки: Полевая приёмка TASK-010.02 подтверждена без пропусков; остальные P0 подтверждены либо официально пересмотрены; оставшиеся риски сообщены; production deploy только отдельным разрешением. Публичный релиз разрешён отдельным решением владельца.

## Ожидаемый результат

Работоспособные компоненты данного этапа, подключённые к существующему приложению; соответствующие миграции, API/UI/инфраструктура (где предусмотрено), автоматизированные тесты и подтверждённые результаты проверок.

## Правила выполнения и завершения

- Прочитать AGENTS.md и перечисленные документы, сверить зависимости и существующий код. При конфликте требований остановиться и зафиксировать вопрос, не менять согласованный контракт самостоятельно.
- Выполнять одну подзадачу за раз в порядке списка; все предыдущие подзадачи этого файла являются зависимостями, если явно не согласован иной порядок. Не переходить к следующей без указания владельца. Отмечать чекбокс только после выполнения критериев; при блокере указать partial/blocked.
- Для задач реализации писать настоящий код, миграции, конфигурации и тесты; подключать компоненты к приложению. Не заменять обязательную функциональность заглушками. Тестовые doubles допустимы только в тестах или явно обозначенном dev режиме.
- Проверять безопасность, owner scope, ошибки и ограничения там, где применимо. Не использовать реальные production secrets, не выполнять push/deploy без разрешения. Не добавлять функциональность других этапов заранее.
- Запускать применимые проверки из TESTING.md: unit/integration, race для конкурентного Go-кода, frontend lint/typecheck/build и E2E, migration/security checks. Записать фактическую команду, результат и непроверенные условия. Не утверждать, что тест прошёл, если он не запускался.
- Обновить затронутую документацию, список изменённых файлов, ADR при необходимости и статус ROADMAP. Весь этап завершён только после прохождения всех подзадач и итоговых критериев. Остановиться после отчёта.
