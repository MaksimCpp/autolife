# TASK-005 — Execution и очередь

Статус: planned. Зависимости: 003,004.

## Цель

Написать работающее ядро фонового выполнения с River и PostgreSQL.

## Источники требований

AGENTS.md; docs/ROADMAP.md; docs/REQUIREMENTS.md; docs/TESTING.md. Дополнительно (пути относительно docs/): modules/WORKFLOW_ENGINE.md, DATABASE.md, API.md, ANALYTICS.md, SECURITY.md.

## Подзадачи и критерии приёмки

### TASK-005.01 — Состояния выполнения

- [ ] Статус: planned.
- Зависимости: зависимости этапа, указанные выше.
- Реализация: Написать модели Execution/StepExecution/ExecutionAttempt, допустимые переходы, миграции executions/steps/attempts и репозитории с атомарным compare-and-set. Реализовать состояния и таблицу переходов WORKFLOW_ENGINE и ADR-002.
- Критерии приёмки: Unit тесты всех переходов; terminal state не возвращается в running; конкурентное завершение имеет одного победителя. Покрыть все запрещённые переходы, оба таймера, attempt 1–3 и stale fence.

### TASK-005.02 — Атомарный запуск

- [ ] Статус: planned.
- Зависимости: TASK-005.01.
- Реализация: Реализовать POST /workflows/{id}/executions: проверка owner/version/config/input, pin файлов, quota reservation, idempotency key, создание execution и River enqueue в одной транзакции. Включить snapshot test-execution, outbox и hash запроса в ту же транзакцию. Схема outbox и базовые producers должны быть доступны с TASK-002.
- Критерии приёмки: Rollback не оставляет принятую задачу; одинаковый ключ возвращает тот же ID, другой payload даёт 409; crash после commit не теряет job. Rollback не оставляет job, pin, reservation, idempotency record или событие. Тестовый запуск не меняет активную версию.

### TASK-005.03 — Воркеры и план исполнения

- [ ] Статус: planned.
- Зависимости: TASK-005.02.
- Реализация: Написать River worker, получение версии, последовательный запуск registered handlers, data resolver, запись step input/output refs и результатов.
- Критерии приёмки: Цепочка из тестовых действий выполняется в порядке; ошибочный шаг останавливает следующие; HTTP возвращает 202 без ожидания.

### TASK-005.04 — Координация и восстановление

- [ ] Статус: planned.
- Зависимости: TASK-005.03.
- Реализация: Использовать поддерживаемые механизмы River, добавить fencing/lease только где нужен domain state; проверять владение перед commit, восстановить queued/running/retrying/cancel_requested и orphan reservations. Возобновлять с последнего проверенного checkpoint, подтверждать остановку старого launcher и чистить staging по ADR-002.
- Критерии приёмки: Два воркера и повторная доставка не создают два логических результата; старый воркер не перезаписывает итог; crash до/после commit протестирован. Просроченный worker не может ни опубликовать объект, ни освободить чужой резерв.

### TASK-005.05 — Повторные попытки

- [ ] Статус: planned.
- Зависимости: TASK-005.04.
- Реализация: Классифицировать ошибки, сохранять attempts, ограничить до согласованного числа, backoff+jitter с учётом дедлайна; не повторять permanent/unknown external outcome. Попытка сохраняется до вызова и учитывается при crash. Максимум 3 на шаг, включая первую.
- Критерии приёмки: Временная ошибка восстанавливается; постоянная завершает задачу; retries не считаются новыми execution. Сбой не сбрасывает счётчик, UNKNOWN_OUTCOME не повторяется вслепую.

### TASK-005.06 — Отмена и дедлайны

- [ ] Статус: planned.
- Зависимости: TASK-005.05.
- Реализация: Реализовать cancel API, durable cancel request, context cancellation, таймауты и передачу сигнала sandbox, предотвращение новых шагов. Развести 30 минут до первого запуска и 15 минут обработки с retries/backoff. Описать конкурирующие terminal CAS.
- Критерии приёмки: Отмена очереди/активной задачи и гонка с завершением имеют корректный итог; процесс остановлен; 15 минут или утверждённый лимит соблюдён. Проверить deadline equality, cancel vs commit, удержание ресурсов до остановки и повтор отмены.

### TASK-005.07 — Учёт ресурсов

- [ ] Статус: planned.
- Зависимости: TASK-005.06.
- Реализация: Ограничить concurrent runs, резервировать и освобождать квоты и pins атомарно, вести actual usage, cleanup после crash; добавить GET /usage. Учитывать глобальные и per-owner пределы очереди, промежуточные ресурсы и cleanup при удалении аккаунта.
- Критерии приёмки: Параллельный старт не превышает лимит; success/fail/cancel освобождают ресурсы; reconciliation восстанавливает зависшие записи. Параллельные запросы не обходят границы, actual и reserved сходятся после restart.

### TASK-005.08 — Результаты и API

- [ ] Статус: planned.
- Зависимости: TASK-005.07.
- Реализация: Реализовать GET /executions, GET /executions/{id}, POST retry с исторической версией и retained/new inputs; безопасные ошибки и expiry. Обеспечить outbox terminal events, историю снимка, отказ retry для архива и понятные expired refs. Включить данные executions в export/delete.
- Критерии приёмки: Retry создаёт новый ID; чужое выполнение недоступно; истёкший файл требует новой загрузки; контракт проверен. Проверены повтор retry с тем же ключом, новый ключ, stale inputs и запрет частичного success.

### TASK-005.09 — Outbox и метрики

- [ ] Статус: planned.
- Зависимости: TASK-005.08.
- Реализация: Расширить общий outbox потребителями и метриками execution с event_id, allowlist payload, запись событий в транзакции состояния, повторяемую доставку; метрики queue/latency/error/retry без user_id labels. Проверить атомарный checkpoint consumer и logical dedup.
- Критерии приёмки: Сбой publisher не теряет событие; duplicate delivery безопасна; содержимое файлов отсутствует в событиях. Двойная доставка и восстановление между эффектом и ack сохраняют один логический результат.

### TASK-005.10 — Graceful shutdown и проверки

- [ ] Статус: planned.
- Зависимости: TASK-005.09.
- Реализация: Подключить остановку при сигнале, прекратить приём задач, корректно завершить/освободить активные работы; интеграционные тесты с PostgreSQL/River и race detector.
- Критерии приёмки: Принятые задачи не теряются при проверенных сбоях; все ожидаемые terminal states, quota/duplicate/crash tests проходят.

## Ожидаемый результат

Работоспособные компоненты данного этапа, подключённые к существующему приложению; соответствующие миграции, API/UI/инфраструктура (где предусмотрено), автоматизированные тесты и подтверждённые результаты проверок.
