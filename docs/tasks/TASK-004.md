# TASK-004 — Workflow definitions и registry

Статус: planned. Зависимости: 002.

## Цель

Реализовать определения сценариев, версии и расширяемый реестр действий.

## Источники требований

AGENTS.md; docs/ROADMAP.md; docs/REQUIREMENTS.md; docs/TESTING.md. Дополнительно (пути относительно docs/): modules/WORKFLOW_ENGINE.md, DATABASE.md, API.md.

## Подзадачи и критерии приёмки

### TASK-004.01 — Доменные модели

- [ ] Статус: planned.
- Зависимости: зависимости этапа, указанные выше.
- Реализация: Написать Workflow, Draft, Version, Step, Binding, Trigger, ActionDefinition; миграции workflows/drafts/versions и репозитории. Описать неизменяемые draft snapshots и составную связь active_version. Подключить workflow к export/delete.
- Критерии приёмки: Версия неизменяема; owner и FK проверяются; draft имеет revision. Принадлежность workflow/version/snapshot обеспечена составным FK.

### TASK-004.02 — Реестр

- [ ] Статус: planned.
- Зависимости: TASK-004.01.
- Реализация: Реализовать регистрацию type/version, схем config/input/output, capability и handler contract; зарегистрировать core.manual и тестовое действие только для тестов.
- Критерии приёмки: Дубликат регистрации отклоняется; новое действие добавляется без изменения engine; тестовый handler не доступен в production.

### TASK-004.03 — Валидация

- [ ] Статус: planned.
- Зависимости: TASK-004.02.
- Реализация: Написать проверку линейного графа, циклов, связей, обязательных полей, типов, лимита шагов и ссылок на файлы; возвращать field/step errors. Канонический порядок задавать массивом steps, проверить ports и bindings.
- Критерии приёмки: Некорректные графы, ссылки вперёд, неизвестные версии и несовместимые типы отклоняются; неполный черновик сохраняется. Связь с будущим шагом, цикл и конфликт типов отклоняются.

### TASK-004.04 — Data binding

- [ ] Статус: planned.
- Зависимости: TASK-004.03.
- Реализация: Реализовать типизированное разрешение trigger/step/constant/user_input, артефактные ссылки вместо бинарных данных; валидацию output.
- Критерии приёмки: Тесты цепочки и несовместимости; чужой artifact отклоняется; нет исполнения произвольных выражений.

### TASK-004.05 — Workflow API

- [ ] Статус: planned.
- Зависимости: TASK-004.04.
- Реализация: Реализовать CRUD/archive/copy, PUT draft с expected revision, validate, publish immutable version, GET actions/triggers; обновить OpenAPI. Публиковать с expected_revision, перечислять версии, emit workflow.* по ANALYTICS.
- Критерии приёмки: Два редактора получают 409 при конфликте; копия независима; публикация атомарна; чужие записи возвращают безопасную ошибку. Конкурентные публикации соблюдают revision и scope, редактирование не меняет предыдущую версию.

### TASK-004.06 — Совместимость

- [ ] Статус: planned.
- Зависимости: TASK-004.05.
- Реализация: Зафиксировать schema_version и action version policy, проверку недоступных действий, безопасное архивирование и повторное использование.
- Критерии приёмки: Старый запуск не меняется при редактировании; архив нельзя запускать; версия не подменяется молча.

## Ожидаемый результат

Работоспособные компоненты данного этапа, подключённые к существующему приложению; соответствующие миграции, API/UI/инфраструктура (где предусмотрено), автоматизированные тесты и подтверждённые результаты проверок.

## Правила выполнения и завершения

- Прочитать AGENTS.md и перечисленные документы, сверить зависимости и существующий код. При конфликте требований остановиться и зафиксировать вопрос, не менять согласованный контракт самостоятельно.
- Выполнять одну подзадачу за раз в порядке списка; все предыдущие подзадачи этого файла являются зависимостями, если явно не согласован иной порядок. Не переходить к следующей без указания владельца. Отмечать чекбокс только после выполнения критериев; при блокере указать partial/blocked.
- Для задач реализации писать настоящий код, миграции, конфигурации и тесты; подключать компоненты к приложению. Не заменять обязательную функциональность заглушками. Тестовые doubles допустимы только в тестах или явно обозначенном dev режиме.
- Проверять безопасность, owner scope, ошибки и ограничения там, где применимо. Не использовать реальные production secrets, не выполнять push/deploy без разрешения. Не добавлять функциональность других этапов заранее.
- Запускать применимые проверки из TESTING.md: unit/integration, race для конкурентного Go-кода, frontend lint/typecheck/build и E2E, migration/security checks. Записать фактическую команду, результат и непроверенные условия. Не утверждать, что тест прошёл, если он не запускался.
- Обновить затронутую документацию, список изменённых файлов, ADR при необходимости и статус ROADMAP. Весь этап завершён только после прохождения всех подзадач и итоговых критериев. Остановиться после отчёта.
