# ADR-001 — Изоляция файлового обработчика

Статус: принят в TASK-000. Верификация: TASK-003.05/06, TASK-007.01 и TASK-010.02.

## Решение

На Linux операторский launcher запускает одноразовый непривилегированный контейнер на задание с фиксированным allowlist профилей и проверяемых аргументов. Интерфейс worker → launcher принимает ID задания, профиль и ссылки на выделенное launcher рабочее пространство. Worker управляет загрузкой входов и сохранением проверенных выходов. Обработчик видит только выделенные входы и выходной каталог. Worker и API не получают произвольного управления runtime. Рабочие каталоги управляются launcher, пользовательские пути и произвольные host mounts запрещены.

Профиль включает read-only root, отдельное ограниченное рабочее пространство, выключенную сеть, drop capabilities, no-new-privileges, seccomp и AppArmor либо эквивалент, cgroup CPU/RAM/PIDs, дисковый лимит и timeout. В контейнер не передаются credentials, доступ к PostgreSQL, объектному хранилищу или runtime. Команды формируются из фиксированного списка аргументов. Launcher при отмене и timeout завершает группу процессов, подтверждает остановку, удаляет workspace. При рестарте отдельный cleanup сверяет рабочие пространства и запущенные задачи. При невозможности применить профиль запуск запрещён.

В MVP PDF допускается только по профилю SECURITY.md. Профили изображений и PDF раздельны. Нативные парсеры оставляют остаточный риск общего ядра. При недостаточной изоляции нужен отдельный узел или VM и отдельный ADR. Проверки выполняются на целевом Linux runtime. Локальный Docker Compose обеспечивает разработку и интеграционные тесты в поддерживаемом Linux окружении.

## Применение к расширенному FileFlow

TASK-007A сохраняет принятую границу и добавляет фиксированные профили документов, HTML и таблиц, расширяет профили растров и PDF. TASK-015 добавляет аудио/видео на той же границе. Отдельные digest, конфигурация ресурсов и fail-closed preflight обязательны; профиль назначает сервер. HTML требует также действующую браузерную песочницу. Проверки добавлены в TASK-007A и TASK-010.02.

## Граница проверок TASK-003 и TASK-010

TASK-003 реализует границу и проверяет fail-closed, парсеры и файловую бизнес-логику на доступном стенде. Полевая проверка профилей на Linux с AppArmor/cgroup v2 обязательна в TASK-010.02 и блокирует TASK-010.09. Сокет Docker остаётся только у оператора launcher; API обращается к выделенному Unix-сокету инспекции. Локальные тестовые адаптеры не входят в рабочие сборки.

## Профиль image-transform TASK-006

Для одноразовой обработки оператор задаёт отдельный digest. Worker передаёт ограниченный поток и фиксированные параметры по Unix-сокету. Launcher задаёт команду, отключает сеть, проверяет профиль и использует отдельный tmpfs 384 МиБ при 512 МиБ RAM, 1 CPU, 32 PID и 30 секундах на растр. Доступ к S3 остаётся у worker. Launcher подтверждает остановку по attempt UUID, сначала устойчиво закрывая повторный запуск для этого ID. Короткий срок запроса проверяется по абсолютному дедлайну. Подтверждение работы этих ограничений на целевой конфигурации остаётся в TASK-010.02/.09.

## Профиль pdf-transform TASK-007

Выделенная digest-сборка запускает фиксированный PDF-обработчик. Worker передаёт бинарные фреймы с ограниченным заголовком и файлами по операторскому Unix-сокету. Ключи S3 и имена пользователя остаются у worker. Профиль использует 1 CPU, 768 МиБ RAM, 768 МиБ tmpfs, 32 PID и 90 секунд на запуск. Проверка AppArmor/cgroup v2 и подтверждение остановки используются из общего launcher. При недоступности профиля действия скрыты. Полевая проверка остаётся в TASK-010.02/.09.

Ответ преобразования ограничен 250 МБ данных плюс фрейминг и буферизуется до успешного завершения. Общий HTTP-лимит допускает до двух ответов преобразования одновременно. Пик RAM launcher под этой нагрузкой проверяется перед релизом в TASK-010.

## Профиль Office в TASK-007A

Оператор закрепляет digest Office-образа для маршрутов `office` и `office-transform`. Один запуск получает ограниченный поток байтов и фиксированный заголовок операции. Данные хранилища и идентификаторы пользователя остаются у платформы. Профиль использует 1 CPU, 768 МиБ RAM, 384 МиБ tmpfs, 32 PID, 40 секунд и один одновременный Office-запуск. Для UNO используется локальный pipe внутри одноразового контейнера. Выход проверяется существующим статическим PDF-валидатором перед передачей в staging. Полевая проверка остаётся в TASK-010.02/.09.

### HTML и таблицы

Профили `html`/`html-transform` и `table`/`table-transform` указывают на отдельные digest. Таблицы ограничены 1 CPU, 512 МиБ RAM, 384 МиБ tmpfs, 32 PID и 35 секундами. HTML ограничен 1 CPU, 1024 МиБ RAM, 512 МиБ tmpfs, 32 PID и 65 секундами. Одновременно допускается один контейнер на профиль. Доступность HTML требует успешной печати стартового документа с включённой браузерной песочницей. Наблюдатель ресурсов читает только endpoint Docker stats выданного launcher контейнера. API, worker и контейнеры доступа к Docker socket не получают.

Функциональная приёмка HTML, включая обе границы песочницы, закреплена за TASK-010.02. До неё оператор оставляет HTML-профиль недоступным. Это условие дополняет стартовую пробу печати.
